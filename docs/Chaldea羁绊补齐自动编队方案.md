# Chaldea 羁绊补齐自动编队方案

## 1. 目标、边界与结论

在现有「Chaldea 自动编队」成功完成后，提供一个可选的第二阶段：在**不替换
Chaldea 已指定从者、助战或礼装**的前提下，使用剩余的本地从者位和未占用的礼装
位，尽量提高五名本地从者的单次羁绊点总和。

本功能是独立的 Custom Action，不修改
[`agent/custom/formation_action.py`](../agent/custom/formation_action.py)。原 Action
目前会自行点击一次「编队决定」，因此新 Action 的运行方式是：

```text
现有 Chaldea 自动编队成功并确认
  -> 新 Action 重新进入“配置变更”页
  -> 识别 COST、可补空槽、现有羁绊礼装
  -> 规划并补齐从者/礼装
  -> COST 与羁绊复核
  -> 再次点击“编队决定”
```

这是一种两阶段提交：即使新功能在 OCR、资源或仓库查找阶段失败，第一阶段已完成
的 Chaldea 队伍不会被回退或被旧脚本改写；新 Action 只会在安全条件满足时继续。

范围：

- 仅处理六槽中的本地从者；助战不选择、不替换、不编辑其礼装，且完全不进入
  羁绊计算范围。助战携带的礼装效果也不作为本地从者的收益来源。
- 仅填充 Chaldea `team` 中未指定本地从者的、且当前游戏界面仍为 `SELECT` 的空位。
- Chaldea 已显式配置 `equip1/ceId` 的本地槽位永远受保护，即使礼装自动编队开关
  已关闭也不允许本功能覆盖该槽位。
- 仅使用本地数据中有实际羁绊公式、且列表与编队模板均齐全的礼装。
- 不使用 `event_id` 条件的活动限定羁绊效果；它们已归档，但默认不作为常驻收益。

## 2. 新选项

在 `Chaldea 自动编队` 任务新增一个总开关和两个仅在开启时显示的子选项：

| 选项 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `自动补齐从者和羁绊礼装` | 是/否 | 否 | 否时新 Action 直接成功返回，不产生点击。 |
| `补齐从者优先X星` | 0–5 星 | 5 星 | 每次补人先尝试该星级；若无可选项，再按 5→0 星、跳过已尝试星级的顺序回退。 |
| `羁绊基础值` | 正整数输入 | 1200 | 用于比较固定值与百分比羁绊礼装；作为 `bond_base` 传给新 Action。 |

例如优先 3 星时，尝试顺序为 `3, 5, 4, 2, 1, 0`。星级是**候选优先级**，不是
无视 COST 的强制要求：每个候选仍必须通过预估 COST 和实际 OCR COST 校验。

开关应在原自动编队完成后才触发新节点；原「自动编成礼装」关闭时，原流程仍视为
礼装阶段完成，新功能照常运行，但会保护 Chaldea 分享数据中已声明的礼装槽位。

## 3. 需要的新文件与数据

实现时只新建以下文件，不在原自动编队 Python 文件中插入羁绊逻辑：

| 文件 | 职责 |
| --- | --- |
| `agent/custom/bond_completion_action.py` | 新 Custom Action，负责识别、规划、选择与复核。 |
| `agent/custom/bond_matcher.py` | 无 UI 依赖的纯函数：从者特性归一化、礼装目标匹配、羁绊评分、候选排序。 |
| `agent/custom/bond_completion_costs.json` | 由 Atlas 离线生成的 `servant_id/equip_id -> cost` 索引；运行时绝不联网。 |
| `tools/update_bond_completion_costs.py` | 增量更新上述 COST 索引的维护工具。 |
| `assets/resource/base/pipeline/羁绊补齐自动编队.json` | 新 Action 专用 pipeline：进入/退出选择页、筛选、复位顶部、单次下滑、等待、筛选确认与最终决定。 |
| 独立 option/task JSON | 新 Action 的入口、开关与 OCR 调试节点；不改变原 Action 的业务代码。 |

`羁绊补齐自动编队.json` 的节点可从现有 `自动编队.json` 的同类流程复制，但必须使用
独立的 `羁绊补齐-` 节点名。新 Action 不直接调用或覆盖既有 `自动编队-*` pipeline，
避免同时运行、覆盖动态筛选参数或以后调整原流程时产生隐式耦合。

现有数据的使用方式：

- `servant_list.json` 提供 `id`、职阶、星级、图片与 `bond` 特性；当前不含 COST，
  因而由 sidecar 索引补齐。
- `equip_list.json` 提供礼装 ID、星级、筛选分类及 `bond`。`bond.bonus_type !=
  "none"` 的常驻效果才进入候选；`atlas_effects` 仅用于审计和排除活动条件。
- `FGO牵绊计算器（优化版）.html` 仅作为公式和目标匹配规则的参考来源；运行时不
  执行 HTML/JavaScript，也不从网页读取数据。

新 Action 直接读取现有编队礼装使用的 `EquipFaces/list` 与 `EquipFaces/team` 资源，
不复制图片文件。2026-09-05 的开发资源实测：59 张常驻羁绊候选中 16 张同时具备
list/team 模板，另外 43 张新增归档记录尚未落入这两个图片目录；运行时会逐项校验，
缺图对象明确记录 ID 并跳过，不会误点仓库首项。以后补入对应图片即可自动扩大候选池。

## 4. 状态与界面识别

### 4.1 槽位与保护规则

复用既有六个从者槽 ROI 和礼装 ROI。新 Action 重新读取 Chaldea 分享数据，建立：

```text
protected_servant_slots = Chaldea 指定 LOCAL 或 SUPPORT 的槽位
protected_equip_slots   = Chaldea LOCAL 槽中 equip_id 非空的槽位
fillable_slots          = Chaldea EMPTY 且游戏识别为 SELECT 的非助战槽位
fillable_equip_slots    = 本功能新填从者的空礼装位
                         + 非 protected_equip_slots 的现有本地从者空礼装位
                         （助战槽永远不在此集合中）
```

`fillable_slots` 还必须满足“当前全队本地从者少于 5”。已有助战占一格时最多五名
本地从者；不存在助战、或本地人数已满五人时均不补人。若 Chaldea 未指定的槽位已被
用户原有从者占据，不清空、不替换，也不把它视为可补空位。

### 4.2 COST OCR

每次计划前、每次选从者后、每次选礼装后，以及最终提交前，从截图的基准 ROI
`[915, 671, 154, 43]`（按屏幕比例缩放）运行 Maa `JOCR`。识别文本必须匹配：

```text
^\s*([0-9,]+)\s*/\s*([0-9,]+)\s*$
```

解析为 `used_cost / max_cost`。OCR 为空、格式不合法、`used > max` 或连续两次结果
不一致时，停止后续新增操作并保留当前编队；不得用估算值继续点击。

候选的 Atlas COST 只用于点击前的保守判断：

```text
used_cost + servant_cost + 已预留的礼装_cost <= max_cost
used_cost + equip_cost <= max_cost
```

实际 UI COST 是唯一提交依据。COST 不足时按所处阶段恢复：

- 补从者阶段：跳过当前候选，在已扫描的拥有列表中换 COST 更低的从者；当前星级没有
  可放入对象时，继续按既定星级顺序扫描更低 COST 的其他星级，直到找到可用者或所有
  候选都放不下。
- 补礼装阶段：先放弃当前礼装并尝试收益次优且 COST 更低的礼装；仍超限时，只卸下本
  Action 新增的礼装，按“边际羁绊收益最低”顺序回退，直到 OCR 确认不超限。Chaldea
  指定礼装和运行前已有礼装永远不卸下。

### 4.3 可用性与图片

从者或礼装只有在以下条件同时成立时才可被选择：

1. 数据库含 ID、星级、特性/公式和 COST；
2. 对应的列表图片模板存在；
3. 当前筛选后的仓库列表实际匹配到模板；
4. 点击后返回编队页，且截图复核成功。

找不到即标记为本轮 `unavailable`，后续规划不再重复尝试。礼装需同时有 list/team
模板；从者需有列表模板，选后在编队槽的模板复核也必须通过。

### 4.4 从者库存扫描

从者的“拥有与否”不能由数据库推断，必须从游戏仓库确认。每个星级采用两次查找：

1. 进入从者选择页后，运行专用 pipeline 复位列表顶部、重置筛选并仅选择当前星级。
2. Python 从初始稳定截图及之后每次稳定截图中，对**该星级优先级列表的全部候选从者**
   做模板匹配，收集全部命中的 `servant_id`；此阶段绝不点击从者卡。
3. 每轮截图扫描完，运行 pipeline 的“单次下滑 + 等待稳定”节点，再继续匹配；最多
   下滑 15 次。可额外以滚动条到底模板提前结束，但“15 次”是稳定的安全上限。
4. 扫描完整个当前星级后，才用已发现的全部拥有从者进行羁绊/COST 计算，选出唯一的
   最终目标。
5. 再运行“复位顶部” pipeline，以最终目标的模板执行第二次定位、下滑和选择；成功
   返回编队页后，必须做头像与 COST 复核。

若当前星级扫描结果为空，则先运行复位顶部 pipeline，再切换到下一个星级重新扫描。
若扫描到了从者但当前最优对象不满足 COST，则在已拥有集合内依次尝试更低 COST 对象；
当前星级全部放不下时继续下一星级。所有星级都无可放入对象才结束补人阶段。

## 5. 羁绊计算模型

### 5.1 与参考计算器一致的常驻公式

对每名本地从者，按参考 HTML 的顺序计算：

```text
step1 = 前排 ? 20% : 0%
intermediate = floor(bond_base * (1 + step1))

step2 = 所有已装备常驻百分比羁绊礼装中、对该从者匹配的百分比之和
result = floor(intermediate * (1 + step2)) + 所有 flat_per_servant 固定值
team_score = 五名本地从者 result 的总和
```

`bond_base` 影响“+50 固定值”与百分比礼装之间的优先级。任务提供“羁绊基础值”输入，
默认 1200；用户可按具体副本修改。脚本必须在日志中写出最终采用值，输入不是正整数时
明确报错，不得静默猜测。

`team_score`、`step1` 与 `step2` 均只使用五名本地从者和本地礼装。助战的从者特性、
所在前/后排、礼装和礼装效果全部排除；因此不会触碰助战礼装 ROI，也不特别处理助战
午茶时光等效果。

### 5.2 特性匹配

`bond_matcher.py` 复刻参考工具的纯数据规则：

- `all` 匹配每名本地从者；
- 普通目标与从者的基础特性、阵营、性别、职阶、灵基和灵衣特性匹配；
- 组合目标单独判断：`lawful_good`、`lawful_female`、`chaotic_seven`、
  `star_or_evil`、`beast`；
- `flat_per_servant` 不以从者特性筛除，按每位本地从者累计；
- 带 `event_id` 的 Atlas 条件默认排除，直到将来显式增加活动选择器。

对于新增从者，点击的图片模板会记录灵基/灵衣变体；评分取实际将被选中的变体，
而不是臆测最高特性。Chaldea 已指定从者的特性直接按其已知 ID 和当前可识别的变体
计算；无法识别的残留从者不替换，且日志标明其未参与“最大化”比较。

## 6. 规划与执行算法

### 阶段 A：建立固定状态

1. 读取 Chaldea 队伍及任务选项；总开关关闭则立即成功返回。
2. 重新进入配置页，确认六槽、助战位置、可补空位及保护礼装位。
3. OCR 当前 COST；识别本地从者已装的候选羁绊礼装，把它们固定在评分模型中。
4. 载入满足数据和模板条件的常驻羁绊礼装候选；已装备礼装不重复选取。

### 阶段 B：先规划礼装，再选择从者

为避免“先塞高 COST 从者，导致最优礼装装不下”，先按当前固定从者计算每张礼装的
边际团队收益；对最多可用的空礼装位进行有 COST 约束的束搜索（beam search）。
评分同时估计剩余空位可加入的从者对每张礼装目标的覆盖数。

在得到礼装组合后，按星级顺序为每个从者空位生成候选：

1. 先尝试用户优先星级；若该星级在完整扫描中没有任何匹配对象，才按 5→0 星回退。
2. 每个星级先按第 4.4 节完整扫描，得到用户实际拥有的候选集合；不在扫描过程中
   点击“看起来最优”的第一名。
3. 同星级的实际拥有候选按“加入后 `team_score` 的增量、匹配礼装数、剩余 COST、ID”
   降序稳定排序，计算出唯一最终目标。
4. 复位列表后只查找并选择该最终目标；选择成功且 OCR COST 符合计划才入队。
5. 每成功选择一人就重新计算礼装组合和下一空位的星级扫描/排序。

候选从者的尝试顺序严格服从用户指定星级；束搜索只决定同一优先层内、并且已经通过
完整仓库扫描确认拥有的从者之间的“羁绊最大化”排序，不能跳过优先星级直接选择更高
收益的其他星级。

### 阶段 C：补齐礼装

从者阶段结束后再次 OCR COST，并基于实际已选从者重新求解礼装组合：

1. 所有 Chaldea 指定礼装位、已识别到的现有礼装均视为固定，绝不替换。
2. 仅将新选从者的礼装位和确认为空、非保护的本地礼装位加入可填集合。
3. 以 `team_score` 边际增量/COST 为主排序；每种本地礼装最多使用一张，不识别或利用
   同名礼装的多副本。
4. 对每张计划礼装执行“筛选 → 模板查找 → 选择 → 编队图复核 → OCR COST”。
   仓库没有该礼装则拉黑、重新规划其余礼装，不中断已选从者。
5. COST 不足时先换用更低 COST 的次优礼装；仍不满足则卸下本 Action 新增、边际收益
   最低的礼装并重新规划。没有正收益、没有空位或所有组合均无法满足 COST 时停止；
   不为了填满格位选择无羁绊效果礼装。

### 阶段 D：最终验证

最终从新截图重建实际状态，并进行三项检查：

1. COST OCR 合法且 `used <= max`；
2. 每个保护的从者/礼装槽仍符合 Chaldea 原配置，新增对象均位于允许空位；
3. 用实际识别到的从者、礼装、变体和 COST 重新计算 `team_score`。若与最终计划不一致，
   不点击决定；若一致，记录“基线分 → 最终分、增量、剩余 COST、未找到对象”。

在已经确认拥有或已经尝试过的候选集合内，再跑一次同样的组合搜索；若存在满足 COST
且更高分的替换，只允许替换本 Action 自己新放入的对象并复核。这样“最大化”的定义是
**已确认候选池内的最优解**。未进行全仓扫描的首版不能诚实宣称是玩家全仓的数学全局
最优；如需全局保证，后续可增加耗时较长的“扫描所有羁绊礼装库存”模式。

## 7. 安全失败与日志

问题按“可恢复”和“不可确认”两级处理；日志和任务结果必须给出明确原因，不能只输出
“补齐失败”：

- 可恢复：某个候选不存在、COST 不足但可降级、个别候选缺资源、没有更优组合。排除或
  回退该候选后继续；最终状态可完整复核时，提交安全的部分结果并将任务记为成功，同时
  输出 `bond_completion_partial` 或 `bond_completion_no_change` 及具体原因。
- 不可确认：连续 COST OCR 失败、保护槽变化、页面状态未知、选择后无法确定实际对象。
  停止点击并尝试退出本次编辑、恢复第一阶段已经确认的 Chaldea 队伍。恢复且复核成功时
  任务记为“成功但未补齐”，输出 `bond_completion_aborted_safe`；无法恢复或无法复核时
  整体任务失败，并输出下表中的精确错误码。

| 错误码 | 条件 |
| --- | --- |
| `bond_completion_cost_ocr_failed` | COST OCR 缺失、格式非法或前后矛盾。 |
| `bond_completion_cost_exceeded` | 预估或实测 COST 超限。 |
| `bond_completion_slot_invalid` | 助战/保护槽/空槽识别不可信。 |
| `bond_completion_resource_missing` | 计划对象缺少必要图片或 COST/特性资料。 |
| `bond_completion_select_verify_failed` | 选从者/礼装后未返回或模板复核失败。 |
| `bond_completion_final_mismatch` | 保护规则、COST 或评分复算不一致。 |
| `bond_completion_restore_failed` | 中止补齐后无法确认已恢复第一阶段队伍。 |

日志至少输出：原 Chaldea 本地槽、可补槽、COST OCR 原文及数值、优先星级队列、每个
候选的拒绝原因、已确认礼装、基线/最终羁绊分、每名从者的命中特性和贡献、最终剩余
COST。不得记录或上传用户的分享链接内容。

## 8. 验收场景

- 开关关闭：原自动编队行为、点击次数和结果完全不变。
- Chaldea 恰好五名本地从者：不补人，只在允许空礼装位补入有收益礼装。
- 仅三名本地从者、一个助战：只填两个真实 `SELECT` 空位，不覆盖任何既有成员。
- 优先 3 星、3 星完整扫描没有命中：复位后按 `3,5,4,2,1,0` 顺序切换筛选并扫描。
- 同一星级多名从者均存在：完整下滑扫描至多 15 次后，再计算唯一最优者；复位列表后
  只选择该对象，不会先点到其他候选。
- 当前最优从者超 COST：先尝试同星级更低 COST 候选，再按星级顺序尝试更低 COST 从者。
- 新增礼装导致 COST 不足：换低 COST 礼装；仍不足时只卸下本功能新增的最低收益礼装。
- Chaldea 已指定礼装、自动编成礼装关闭：该礼装槽仍不得被新功能点击。
- 最优礼装在数据库存在但仓库不存在：标记 unavailable、重新规划其他礼装并继续。
- 活动限定羁绊礼装：归档信息可见，但默认不进入常驻候选。
- OCR 读成非 `XX/XXX`：安全停止，不按预测 COST 继续。
- 个别礼装实际缺少 list/team 模板：跳过并明确输出礼装 ID 与缺失路径，不误点仓库首项。

## 9. 已确认的实施决定

1. 接受原编队确认后重新进入配置页、补齐后再次确认的两阶段流程。
2. 优先星级默认 5 星。
3. `bond_base` 默认 1200，同时提供可修改的正整数输入项。
4. 补从者时 COST 不足则换更低 COST 从者；补礼装时换低 COST 礼装，必要时卸下本功能
   新增的最低收益礼装。
5. 允许给当前没有 Chaldea 指定礼装的本地从者空礼装位补装；已指定位置保持现状。
6. 每种礼装最多选一张，不考虑多副本。
7. 复用现有编队礼装模板库，不新增一套重复模板。
8. 可安全复核时保留部分成果并成功返回；只有状态无法恢复或无法确认时失败，所有问题
   都通过明确状态码、对象 ID、槽位和原因报告。
