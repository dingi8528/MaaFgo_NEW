### F1 结算必命中节点挡住必要处理分支

**位置**：`assets/resource/base/pipeline/原生自动战斗调度.json:198`、`:209`、`:256`；失败交接还涉及 `agent/battle/runtime/runtime.py:109`。

`结束战斗_不回主界面` 在撤退节点之前放置了 `结算推进_点击右上角`，后者为 `DirectHit`。当画面是战败撤退页时，它会先命中，进入自己的循环；该循环没有撤退或撤退确认分支。Python 已明确把 DEFEAT 作为成功交接返回给结算 Pipeline，因此这是一条实际可达的交接路径。

连续出击还有同类问题：`作战成功_结束战斗_继续` 将必命中的 `_继续` 推进节点放在剧情跳过节点前面，而推进节点自己的循环没有剧情跳过。即使开启跳过剧情，战后剧情出现时也无法走到外层的跳过分支，盲点还可能停在跳过确认弹窗。外层补体力分支也被遮挡，但正常点击连续出击后另有补体力入口，不能据此断言所有补体力都失败。

**复现证据**：使用 MaaFramework v5.10.4、内存控制器和受控识别条件，保留原始 `next` 顺序，第一命中分别为：

```text
画面条件为战败撤退 → 结算推进_点击右上角
画面条件为连续场战后剧情 → 结算推进_点击右上角_继续
```

测试仅验证分支选择，没有执行真实点击。后续持续循环的判断来自原始节点图。

**建议**：把必命中的盲点推进节点放到所有有效识别分支之后；同时让它的循环覆盖撤退、确认、剧情等必要状态。连续场和最终场分别定义退出条件，并增加有界的结算推进次数或总时限。

**验收**：胜利、战败、撤退确认、战后剧情、连续出击补体力均能到达对应分支；未知画面能有界失败，而不是持续盲点。

### F2 最后一场经过好友申请后可能继续出击

**位置**：`assets/resource/base/pipeline/原生自动战斗调度.json:123`，尤其是 `next` 的第 141 至 144 行。

单场、最后一场和连续场共用 `好友申请界面_不回主界面`。该节点关闭好友申请后，固定优先进入 `连续出击_继续`，随后还有必命中的 `结算推进_点击右上角_继续`。这里没有保留“本场是否为最后一场”的信息。

**触发条件**：最后一场出现好友申请，关闭后游戏提供连续出击界面。此时即使调度入口选择了“不继续”，共享节点也能把流程重新带到继续按钮，可能额外消耗 AP 并进入下一场。

**复现证据**：内存控制器测试将关闭申请后的可见节点设为 `连续出击_继续`，MaaFramework 确认选择了该节点。`git blame` 显示相关路由早于本次审查时间窗，是最近结算调整中仍保留的缺陷。

**建议**：拆分最终场与连续场的好友申请处理节点，或显式传递结算模式。最终场节点及其后继图不应包含可达的继续出击动作。

**验收**：设置 1 场和 N 场分别测试，最后一场关闭好友申请后不会点击继续；非最后一场仍正常续战。

### F3 库存静止被误判到底并接受零命中结果

**位置**：`agent/custom/inventory_scan_action.py:736`、`:797`、`:891`；写入在 `:190`，消费方在 `agent/custom/bond_completion_action.py:675`。

扫描以“连续三次画面内容差异很小”作为独立的到底条件，没有要求滚动条确实接近底部，也没有用识别失败情况阻止完成。即使首屏重试后仍无命中，扫描也会继续，最后生成 `scan_complete=true`。

这会把滑动未生效、截图缓存持续滞后等异常与“真正到底”混在一起。当画面能检测到卡片但身份识别失败时，`unmatched_candidate_cells` 只记录日志，不影响完成状态。随后原子替换可以完整地写入一份内容错误的库存；原子写入保护的是文件完整性，不能保证扫描结果正确。

**复现证据**：调用实际 `_scan_pages`，设置滚动条中心为 300、每屏可见 24 张卡、身份命中为 0、画面持续相同，并让滑动命令返回成功。第 4 屏得到：

```json
{
  "count": 0,
  "scan_complete": true,
  "pages_scanned": 4,
  "swipes": 3,
  "unmatched_candidate_cells": 96,
  "bottom_confirmed": true,
  "bottom_detection": "content"
}
```

实际 `_read_player_inventory` 接受了该结果。复现只在临时目录读写，没有覆盖真实玩家库存。此问题的内容兜底条件源于较早提交 `c3f6881`；近期修正滚动条高度后仍然存在。

**建议**：检测到卡片却持续零命中时应重试或失败，保留旧库存；内容静止不能单独推断中段到底，应结合滚动条位置、有效滑动进展和短列表证据。把“遍历完成”和“识别质量合格”分别记录并校验。计算识别覆盖率时要区分重复卡片与按 ID 去重的命中数量，不能直接把当前累计差值当作失败率。

**验收**：中段三次滑动无效、缓存不更新、卡片全部不识别均不得覆盖旧库；真实短列表及真实空礼装筛选结果仍能正确处理。

### F4 重建本地库存不会让羁绊记忆失效

**位置**：`agent/custom/bond_completion_action.py:477`、`:591`。

记忆键包含目标编队、偏好、是否使用本地库存等设置，但不包含库存内容指纹或库存版本。只要画面编队签名仍一致、额外从者未满羁绊，`_try_auto_memory_hit` 就提前结束，跳过重新评分。

**触发条件**：获得更优的羁绊礼装或从者后，按说明重建库存，随后继续运行同一任务。当前队伍不变时，即使新库存已成功载入，也可能继续沿用旧方案。更新羁绊数据或优化算法也有类似缓存过期风险。

**复现证据**：调用实际 `_prepare_auto_memory` 保存记忆，再增加 `local_servant_ids` 和 `local_equip_ids`，重新准备记忆；任务键不变，实际命中方法仍返回命中。该测试验证缓存依赖缺失，不是对真实账号的最优收益测量。

**建议**：本地库存模式把规范化持有 ID 集合的哈希纳入键，必要时加入影响选择的库存属性；再增加羁绊数据与优化算法版本。实时扫描模式可提供明确的“重新优化”入口或合理有效期，避免为了验证缓存而每次完整扫描。

**验收**：相同库存、相同设置继续命中；新增候选或相关数据版本变化后至少执行一次完整优化。

## 优化建议

### 让现有回归测试在干净检出和 CI 中真正运行

`tests` 下共有 11 个 `test_*.py`，只有 4 个被 Git 跟踪，另外 7 个受到本机 `/tests/` 排除规则影响。根目录的特殊技能测试已跟踪。本次 134 项通过中，有 91 项来自未跟踪的本机测试，其他协作者无法直接复用这些保护。

`.github/workflows/check.yml` 当前运行 maa-checker 和 JSON Schema 校验，没有运行 Python 回归测试。建议先把有效测试正式纳入版本控制，为库存异常和结算分支补行为测试，再加入 CI。BBC 测试当前读取被忽略的 `BBchannel/settings` 及资料文件，应改用最小、可提交的固定样本，避免 CI 依赖个人安装目录。单元测试与原生框架组件测试可分为两个作业。

### 补齐校验器的覆盖范围和可运行性

`python tools/validate_schema.py ...` 在本机默认 GBK 输出环境下因 `✓` 字符抛出 `UnicodeEncodeError`；加 `-X utf8` 后通过。建议在统一验证入口显式使用 UTF-8，或让状态输出兼容终端编码。

另外，当前 `deps/tools` 缺少 `interface_import.schema.json`。即使显式传入 `--task-dirs assets/tasks assets/options`，校验器仍只打印跳过警告，最后显示通过。建议在明确要求校验任务文件时，对缺失 schema 返回失败；同时增加 import 路径和入口引用完整性校验。maa-checker 的独立检查不应被这个 Schema 结果替代，本次没有重新运行需要动态获取版本的 `npx` 检查。

### 缓存从者目录解析和别名索引

`AutoFormationFromChaldea._get_servant_info` 每次都读取完整 `servant_list.json` 并调用 `build_servant_lookup`。新增别名逻辑后，`_load_servant_templates` 也会调用它；羁绊候选模板准备会多次进入这条路径。

建议按任务加载一次目录和索引，或以文件路径、修改时间、大小作为缓存键，借鉴现有身份索引缓存的失效方式。保留重复 ID 与别名冲突校验。实施前后测量候选模板准备耗时，再决定是否继续优化特征匹配内部的循环；本次未给出未经测量的性能提升比例。

### 把特殊技能的资源覆盖与实机覆盖分开维护

现有特殊技能测试能检查节点、默认入口、图片格式和尺寸，但不能证明按钮在实际游戏中可识别。现有验证文档仍明确记录夏洛特 S3 未解锁、安哥拉曼纽未完成对应强化、但丁未持有，相关 OCR 路径不应视为实机验收完成。

建议保存这些分支的匿名截图样本，增加正例、相似弹窗负例和目标选择后续界面测试。新增选项目前采用固定默认值，其他选项节点没有挂入默认入口；这是当前设计边界。后续如果要支持 Chaldea 攻略逐次指定特殊选项，应连同动作模型、转换器和运行时路由一起实现。
